# Testing

How a kind here is tested, in three layers. The details are in
`docs/fake-cloud.md` (the fake) and `docs/live-runs.md` (live runs and the
ledger); this page is the policy.

## 1. Every kind passes on the fake, on every change

`task check` runs every kind's end-to-end test against the fake cloud:
envtest's kube-apiserver, Config Connector's direct reconciler with our
controllers, and mockgcp with our patches as Google Cloud
(`pkg/test/mockenv`). The kinds generated by `hack/discokind` are served
by `pkg/discokind/fake` in front of mockgcp and all run the same test
(`pkg/discokind/kindtest`): create, a resync that writes nothing, update
(or the API server refusing it, for a kind the API cannot patch), delete,
abandon. Pull requests run `task check:static` plus the changed groups'
tests (`hack/ci/select.sh`); main runs everything nightly. No credentials
reach these tests.

The fake shows what our code does: the requests it sends, the names it
builds, the diff it computes, the status it writes. It cannot show what
the real API refuses or adds: required fields and enum values, cross-field
rules, defaults it fills in, eventual consistency, permissions, quotas.
For the generated kinds that is everything beyond the shape of the
collection. What our code does when a quota refuses it can be shown:
`env.RefuseForQuota(n, match)` (`pkg/test/mockenv`) answers the next `n`
matching requests 429 `RESOURCE_EXHAUSTED` in front of the fake or the
real cloud, and `env.Events` lists an object's event reasons
(`TestDataplexLakeRefusedForQuota`, `TestIAMAccessPolicyRefusedForQuota`).

## 2. Live where the fake gives no signal, sampled over time

`task test-live PROJECT=$GCP_PROJECT KINDS=<package>` runs the same
tests against the real project, only on an offload VM as
`$GCP_LIVE_SA`, never from a
laptop or `task check`. `LIVE_RUN=<regexp>` narrows a package to some
kinds. Every name carries the run's ID, the test deletes what it makes,
and the run ends with the sweeper and an empty `task live-list`.

- **Every kind once.** A kind is not done until it has one live row in
  the ledger (`docs/live-runs.md`). For a generated kind that row is the
  first real signal, so it comes before the kind is promoted past
  `v1alpha1`.
- **Then sampled, cheapest first.** Free resources (saved queries, OAuth
  clients, IAM objects, firewall policies, address groups, secrets) can
  run every time; billed ones (a Cloud SQL instance, a router with NAT,
  anything with an hourly price) run when their code or the pin changes.
  One ledger row per kind per run.
- **Live is required when the fake cannot answer**: a new kind; a fix
  for something live showed; a change in how we call the API (a mask, a
  verb, an operation); a move of the upstream pin that touches the kind.
- **What live finds goes back into the fake**: our bug is a fix plus a
  test; a fake that answered differently is a mockgcp patch, or for a
  generated kind a `fakeDefaults` entry or a note in `docs/fake-cloud.md`
  when the fake cannot show it.
- **Organization and folder kinds** wait for the test folder
  (`live-skip` in a generated kind's fixtures says why), and kinds that
  need a role the account lacks wait for the role: the live-test account
  is never granted anything by an agent. Pending today:
  `LoggingSavedQuery` needs `logging.savedQueries.*`
  (`roles/logging.admin` or a custom role), `IAMOauthClient` needs
  `iam.oauthClients.*` (`roles/iam.oauthClientAdmin`).

## 3. Rechecking the fake against Google Cloud, on a schedule

The fake drifts as the APIs change. A periodic job keeps it honest:

- **Nightly (free kinds) and weekly (the rest)**, a workflow starts an
  offload VM as the live-test account and runs `task test-live` for a
  rotating sample: every generated kind whose resources are free each
  night, the billed kinds round-robin once a week. Each run appends its
  rows to the ledger by a pull request, so a regression is a red row with
  the API's answer in it.
- **A fake/live diff, not only pass/fail.** The same test records the
  requests and answers on both targets (`mockenv`'s request log); the job
  compares the shapes of the answers (field names present, operation or
  not, status codes on the error paths) and flags any field the real API
  returned that the fake did not, as a `fakeDefaults` or patch candidate.
- **The pin's Discovery documents.** When `docs/coverage/sources.yaml`
  moves, `go run ./hack/discokind -check` shows which generated kinds'
  types changed; those kinds go into the next live sample.
- **What it needs** (the builder's): the workflow's identity allowed to
  start an offload VM as the live-test account (the Spot runners already
  start VMs through workload identity), and the roles above. Until then
  the same runs go by hand from a laptop through `offload`.
